# نظام إدارة سكن الموظفين — الإصدار 2.0

نسخة جديدة كاملة من تطبيق السكن، مبنية بنفس تقنيات وهيكلية نظام رحلات السائقين:
**FastAPI + SQLAlchemy/PostgreSQL (Supabase)** للخادم، و**Next.js 16 + React 19 + TypeScript (RTL)**
للواجهة، مع **Capacitor 8** لتطبيق أندرويد، ونشر على **Render**.

> **بيانات الإنتاج محفوظة:** يستخدم الخادم الجديد نفس مستند الحالة في Supabase
> (`kv_store` بالمفتاح `housing_state_v1`) ونفس ملف `data.json` المحلي، لذلك تنتقل
> المباني والغرف والأسرّة والسكان والمستخدمون والمتعهدون دون أي ترحيل يدوي.

| الدليل | شرح الاستخدام ودورة العمل ومفاتيح الاختصار |

### مزايا جديدة في 2.0
- **سجل عمليات (Audit Log)** لكل تعديل حساس مع المستخدم والوقت والتفاصيل.
- **مركز إشعارات** داخل التطبيق مع عدّاد غير المقروء.
- **نسخ احتياطي واستعادة** لمستند الحالة كاملاً (JSON) من لوحة الإدارة.
- **إدارة كاملة للمباني والغرف والأسرّة** مع حماية من حذف عناصر مشغولة.
- **تنقلات الأسرّة (Rotations)**: جدولة نقل ساكن من سرير إلى آخر مع تنفيذ آمن.
- **استيراد/تصدير السكان** عبر CSV، وقوالب جاهزة.
- **تحليلات سعة المتعهدين** ومقارنة السعة التعاقدية بالأسرّة الفعلية.
- **بوابة متعهد** مستقلة: عماله وطلباته وسعته فقط.
- **عمل دون إنترنت (قراءة فقط)** بعد أول دخول ناجح: تخزين نسخة محلية + دخول برمز PIN.
- **بحث شامل** في السكان والمباني والمتعهدين والطلبات والمستخدمين.
- **جلسات JWT** (Access + Refresh) مع تجديد تلقائي وتسجيل خروج.

.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000

كلمات المرور النصية القديمة تلقائياً إلى تخزين آمن (scrypt).

## الحسابات والصلاحيات

الحسابات التجريبية في `seed.json` تستخدم كلمة المرور **`123456`**، وتُرقّى تلقائياً
إلى صيغة scrypt عند أول تشغيل أو أول تسجيل دخول.

| المستخدم | الدور | أبرز الصلاحيات |
| --- | --- | --- |
| `admin` | مدير النظام | جميع الصلاحيات (18) |
| `supervisor` | مراقب السكن | السكان والسكن والتقارير واعتماد طلبات المتعهدين |
| `security` | مشرف الأمن | المتابعة + الاعتماد الأمني |
| `visitor` | مراقب الزوار | المتابعة + اعتماد مرور الزوار |
| `ctr01` … | متعهد/مقاول | بوابة المتعهد فقط |

الأدوار الافتراضية: `r_housing` (مراقب السكن)، `r_security` (مشرف الأمن)،
`r_visitor` (مراقب الزوار)، `r_contractor` (متعهد)، `r_admin` (مدير النظام).
يمكن إنشاء أدوار إضافية وتعديل صلاحياتها من شاشة **إدارة النظام**.

> **مهم:** غيّر كلمات المرور الافتراضية وكلمة مرور `admin` قبل الإنتاج، وفعّل
> `FORCE_PASSWORD_CHANGE=true` إن أردت إجبار جميع المستخدمين على التغيير.

## البيانات والتوافق

### أولوية التخزين
1. إذا كان `DATABASE_URL` مضبوطاً → PostgreSQL/Supabase جدول `kv_store`.
2. إذا كان فارغاً → ملف `backend/data.json`.
3. إذا لم يوجد أي مستند → تُحمَّل البذرة `backend/seed.json`.

### مستند الحالة
مفتاح واحد (`STATE_KEY`) يحوي كائناً JSON بالبنية التالية:

```text
schemaVersion, generatedAt, user, buildings, rooms, beds, residents, requests,
users, contractors, contractorWorkers, contractorRequests, roles, rotations,
settings, permissions, notifications, meta, auditLog, tree
```

- المفتاح الافتراضي: **`housing_state_v1`** — نفس مفتاح النسخة الحالية.
- الكتابة ذرّية: تُكتب نسخة مؤقتة ثم تُستبدل، مع قفل داخلي لكل عملية.
- عند التخزين في Postgres تُنشأ الأعمدة تلقائياً: `key TEXT PRIMARY KEY`,
  `value JSONB`, `updated_at TIMESTAMPTZ`.

### الحفاظ على بيانات الإنتاج
- **لا تغيّر `STATE_KEY`** في Render أو في جدول `kv_store`.
- لا تحتاج إلى SQL ترحيل: الجداول القديمة تبقى كما هي، والنظام يقرأ نفس المستند.
- قبل الترقية، صدّر نسخة احتياطية من لوحة Supabase (**Database → Backups**) أو من
  شاشة **إدارة النظام → نسخ احتياطي**.

## دورة عمل طلبات المتعهدين

**إضافة عامل جديد:** `الأمن` → `مراقب الزوار` → `السكن` → `مكتمل`

**إزالة عامل:** `السكن` → `الأمن` → `مراقب الزوار` → `مكتمل`

- يمكن الرفض في أي مرحلة مع سبب.
- اعتماد السكن لطلب الإضافة ينفّذ التسكين على السرير المحدد بعد التحقق من:
  - السعة التعاقدية للمتعهد (`bedQuota`).
  - توفّر سرير فعلي داخل مبانٍ المتعهد.
  - كود الموظف (إلزامي عند مرحلة الزوار لطلبات الإضافة).
- اعتماد الزوار لطلب الإزالة ينفّذ الإخلاء فعلياً.
- طلب الإزالة يُثبّت `targetResidentId` لسجل العامل عند إنشائه، ويُحذف ذلك السجل فقط؛
  لذلك لا يمكن لطلب استبعاد قديم أن يحذف عاملاً جديداً أُضيف لاحقاً بنفس كود الموظف
  (وهو سبب فقدان العامل `70023` سابقاً).
- كل خطوة تُسجَّل في سجل العمليات وتُنشئ إشعاراً للمرحلة التالية.

## النشر على Render وSupabase

الملف `render.yaml` يعرّف خدمتين:

| الخدمة | النوع | الجذر | التشغيل |
| --- | --- | --- | --- |
| `housing-management-api` | Python | `backend` | `uvicorn app.main:app` |
| `housing-management-web` | Node | `frontend` | `node scripts/serve-static.mjs` |

الخطوات المختصرة:
1. أنشئ مشروع Supabase واحصل على رابط **Session pooler** (مع `sslmode=require`).
2. ارفع المشروع إلى Git، ثم في Render: **New → Blueprint** واختر المستودع.
3. اضبط على خدمة الـ API:
   - `DATABASE_URL` = رابط Supabase.
   - `SECRET_KEY` يُولَّد تلقائياً (32+ حرفاً).
4. اضبط على خدمة الويب:
   - `NEXT_PUBLIC_API_URL` = رابط خدمة الـ API (يُدمج وقت البناء، لذا أعد النشر بعد تغييره).
5. تأكد من نجاح فحص الصحة `/health` ثم افتح رابط الواجهة.

التفاصيل الكاملة في [`docs/RENDER-DEPLOY.md`](docs/RENDER-DEPLOY.md) و
[`docs/SUPABASE-SETUP.md`](docs/SUPABASE-SETUP.md).

## الأمان

- كلمات المرور: scrypt مع Salt، وترقية تلقائية للنص القديم.
- JWT: Access (12 ساعة افتراضياً) + Refresh (30 يوماً)، مع `pv` لإبطال الجلسات عند
  تغيير كلمة المرور.
- تحديد محاولات الدخول (Rate limiting) وسجل تدقيق لكل عملية حساسة.
- رؤوس أمان: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
  `Permissions-Policy`، ومنع التخزين المؤقت لمسارات الـ API.
- في الإنتاج يرفض الخادم الإقلاع بمفتاح `SECRET_KEY` ضعيف، ويعطّل `/docs`.
- راجع [`docs/SECURITY.md`](docs/SECURITY.md) لقائمة التحقق قبل الإنتاج.

## ملاحظات الترقية

- المشروع القديم `housing_mobile_project` (Flutter) لم يُعدَّل إطلاقاً.
- هذا المشروع مستقل تماماً في `housing-management-system/`.
- بيانات الإنتاج: نفس `kv_store` ونفس مفتاح `housing_state_v1` → لا فقدان بيانات.
- بيانات المحلي: نفس مخطط `seed.json` (camelCase) → لا تغيير في الحقول.
- واجهة API متوافقة مع الاستدعاءات القديمة حيث أمكن:
  - `/api/auth/login` يعيد `access_token` و`refresh_token` و`token` معاً.
  - `/api/bootstrap` يحوي القوائم العلوية القديمة (`buildings`, `residents`, …).
